## 本阶段改动

### 1. 歌单顺序（原有实现的缺陷）

V1.02 的 `TrackGroup.trackUris` 是 `Set<String>`，集合不保留插入顺序，因此“歌单播放顺序”在旧实现下无法保证。
现改为 `List<String>`：

- 保存顺序即播放顺序，新增歌曲追加到末尾（`addTracksToGroup`），不覆盖已有顺序。
- 读取时去重但**不重新排序**，所以 V1.02 用户已有的分组不会被打乱。
- `LibraryQuery.resolve` 按保存顺序解析可用歌曲，音频被移动/删除的条目被跳过而不是中断播放。

### 2. 搜索

- 匹配范围从「歌名 / 歌手 / 文件名」扩展到**专辑**。
- 多关键词以空格分隔，采用 AND 语义：`稻香 DEER` 收窄结果而不是放宽。
- 大小写不敏感，命中文字在列表中加粗高亮。
- 逻辑抽到纯 Kotlin 的 `LibraryQuery`，便于单元测试。

### 3. 收藏

- 新增「收藏」标签页，心形按钮在歌曲列表、分组、专辑/艺术家列表均可用。
- 按添加顺序保存并整列播放；音频不可访问时自动跳过。
- 存储在 `favorite_track_uris`。

### 4. 最近播放

- **由播放服务写入**（`PlaybackService.recordPlayed`），因此在通知栏、桌面小部件或恢复队列触发的播放同样会被记录。
- 列表只展示当前仍可访问的本地歌曲，最新在前。
- 历史以 `uri<TAB>时间戳` 文本保存，解析失败的行被丢弃而不抛异常；上限 200 条。
- 不可访问的条目**保留在存储中**，避免存储卡临时卸载时清空用户历史。

### 5. 备份与恢复

- 备份 schema 升级到 2，新增 `favoriteTrackUris` 与 `playHistory`。
- **兼容 V1.02 的 schema 1 备份**：仍可导入。
- 缺少这两个字段的旧备份导入时，会保留现有收藏与历史，而不是清空。

**验证过程与结果：**

| 检查项 | 结果 |
| --- | --- |
| 收藏顺序 | 依次收藏 batch_mp3 → 稻香 → 002起风了，收藏页顺序与操作顺序一致 |
| 收藏持久化 | `am force-stop` 重启后顺序**完全不变** |
| 歌单顺序 | 新建 `OrderCheck`，在「添加歌曲」里**故意乱序勾选**（3rd → 1st → 2nd），保存后歌单内顺序与列表自然顺序一致 |
| 歌单持久化 | 重启后歌单内顺序**完全一致** |
| 播放顺序 | 播放歌单第一首，3 秒曲目播完**自动进入第二首**；按「下一首」依次为 稻香 → 002起风了，与歌单顺序一致 |
| 音频消失 | 把 `dsh_tagtest.mp3` 改名为 `.mp3.bak` 并从 MediaStore 移除后重启：**无崩溃**（进程存活、无 `FATAL EXCEPTION`），重扫后该曲从**曲库、收藏、近期**三处一并消失 |
| 文件还原 | 改回 `.mp3` 并触发媒体扫描，MediaStore 与曲库均恢复 |

**一处值得记录的行为（非缺陷）**：改名后立刻重启，曲库仍显示该曲。原因是
`LibraryCache.MAX_AGE_MS = 5 分钟`——启动时若缓存仍新鲜就**直接用缓存、不重新扫描**
（`startup()` 中 `if (!LibraryCache.isFresh(snapshot)) scanAll()`）。触发一次真实扫描
（设置页「按文件夹」）后即消失。这是为避免每次启动都全盘扫描的有意设计。

`Phase2PersistenceTest`（androidTest）使用真实的设备端 `SharedPreferences`，并以新建实例模拟应用重启，
覆盖持久化契约；该测试由 CI 的 `connectedDebugAndroidTest`（模拟器 API 35）执行并通过。
