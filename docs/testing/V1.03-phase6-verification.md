## 本阶段改动

### 1. 统一 LRC 解析（新增 `subtitles/LrcParser.kt`）

改动前 LRC 的**时间戳计算**和**「哪段文字属于这一行」的规则各写了两遍**，而且两份不一致：

| 位置 | 取文字的方式 |
| --- | --- |
| `SubtitleParser.parseLrc` | 把行内**所有**时间戳都删掉 |
| `PreviewLyrics.parseLrcTimeline` | 取**最后一个**时间戳之后的文字 |

对 `[00:01][00:05]副歌` 这种一行多时间戳的写法，前者会得到 `副歌`，后者也会得到 `副歌`，但对 `[00:01]第一句[00:05]` 这类写法两者结果不同。现在只保留一份实现，采用**播放器面向的规则**（取最后一个时间戳之后的文字），因为一行挂多个时间戳时，文字语义上属于整行。

同一时间戳的多行会合并成一个多行条目（原文 + 译文通常就是这么写的），同一时间戳下的重复文字会去重。

### 2. 小数秒语义（新增 `subtitles/LrcTimestamp.kt`）

`.5` 是 500ms、`.05` 是 50ms —— 即小数部分按**十进制小数**解释，而不是按字符数补零。抽成 `LrcTimestamp` 后所有读取方共用同一份实现。

### 3. 编码识别（新增 `subtitles/SubtitleDecoder.kt`）

旧实现把字节按 UTF-8 解码后**查找 U+FFFD** 来判断「是不是 UTF-8」。这个判断两头都错：

- Java 默认的 UTF-8 解码器遇到非法字节会**静默替换**成 U+FFFD，所以 GB18030 文件只要恰好没被替换就被当成 UTF-8 → 显示乱码；
- 合法的 UTF-8 文本**本身可以包含** U+FFFD，这种文件会被误判成 GB18030 而重新解码。

现在用 `CodingErrorAction.REPORT` **真正校验字节合法性**，而不是靠解码结果猜：

1. 有 BOM 就以 BOM 为准（UTF-8 / UTF-16LE / UTF-16BE），并**剥掉 BOM**，否则首行会多出一个不可见字符；
2. 无 BOM 时，只有字节**确实是合法 UTF-8** 才按 UTF-8；
3. 否则依次尝试 GB18030、Big5；
4. 都失败时按 UTF-8 尽力解码（只替换无法解码的字节），**宁可显示有损内容也不显示空白**。

### 4. 区分「为什么没有歌词」（新增 `subtitles/LyricsLoad.kt`）

原先播放器只有一句「没有找到匹配的歌词或字幕」，把六种完全不同的情况混为一谈。现在每种情况都有自己的文案：

| 结果 | 含义 |
| --- | --- |
| `Loaded` | 正常解析出歌词 |
| `Disabled` | 用户在设置里关掉了自动加载 |
| `NotLinked` | 这首歌没有关联歌词文件 |
| `Unreadable` | 文件关联了但读不出来（被删/无权限） |
| `UnsupportedFormat` | 扩展名不支持 |
| `EmptyFile` | 文件是空的 |
| `NoTimestamps` | 只有 `[ar:]` 之类的标签，没有时间轴（`metadataOnly` 区分「纯标签」和「没时间戳」） |

`LyricsLoad` 是 sealed interface，`lyricsStatusText()` 对每种情况给出具体文案，`when` 是穷尽的 —— 以后新增一种失败原因，编译器会强制补上文案。

### 真机测试（新增 `androidTest/Phase6LyricsTest.kt`，16 项）

单测是在 JVM 里喂字符串，**证明不了「磁盘上的字节 → ContentResolver → 歌词」这条真实链路**。`Phase6LyricsTest` 把真实文件写进设备缓存目录再走完整加载路径：

- UTF-8 / 带 BOM / GB18030 / UTF-16LE 四种编码的中文歌词都能正确显示；
- `[offset:+500]` 使歌词**延后** 500ms、`[offset:-400]` 使其**提前** 400ms、负偏移不会产生负数时间戳；
- 纯标签文件报 `NoTimestamps`、空文件报 `EmptyFile`、`.txt` 报 `UnsupportedFormat`、未关联报 `NotLinked`、文件缺失报 `Unreadable`；
- SRT 字幕走同一入口仍能正常解析；
- 同时间戳的原文+译文合并成一条、乱序文件按时间轴排序。

**结果：`OK (16 tests)`。**

### 离线可用性（已实测）

本地播放与本地歌词是本 App 的核心，**断网必须完全可用**；联网仅用于可选的歌词搜索，且搜索失败不影响本地歌词。

实测方式：关闭 Wi-Fi 与移动数据（`svc wifi disable` / `svc data disable`，确认 `wifi_on=0`、`mobile_data=0`、`ping 8.8.8.8` 100% 丢包）后重跑 `Phase6LyricsTest`。

**结果：断网状态下同样 `OK (16 tests)`。** 验证完成后已恢复 Wi-Fi 与移动数据（`ping` 恢复正常）。

## 已知限制

无 BOM 的 Big5 与 GB18030 在「字节是否合法」这一判据下**无法区分**（短文本尤其如此），因此固定优先尝试 GB18030。若 Big5 文件恰好也是合法 GB18030 字节序列，会被解成 GB18030。这是编码探测的固有限制，不是实现缺陷；带 BOM 的文件不受影响。
