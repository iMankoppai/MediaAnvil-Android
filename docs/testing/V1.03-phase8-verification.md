# V1.03 阶段八验证记录：版本号与发布

测试日期：2026-09-23
设备：vivo V2520A（Android 16 / API 36）
工具链：JDK 17、Android SDK 36（Build Tools 36.0.0）、Gradle 9.6.0

## 本阶段改动

- `versionCode` 3 → **4**，`versionName` "1.02" → **"1.03"**
- README 的发布示例命令同步为 `v1.03`

发布工作流会拒绝对不上的标签：

```
TAG="${GITHUB_REF_NAME:-v$VERSION_NAME}"
test "$TAG" = "v$VERSION_NAME" || { echo "..."; exit 1; }
```

所以版本号与标签必须一致，这也是本阶段唯一必须改的代码。

## 发布前验证

### 1. 签名连续性（决定能否覆盖升级）

| APK | 证书 DN | SHA-256 |
| --- | --- | --- |
| v1.02（已发布） | `CN=MediaAnvil, OU=Release, O=iMankoppai, C=CN` | `56b7d24c…37d3e3` |
| v1.03（本次发布） | 同上 | **同上** |

证书完全相同，因此 1.03 可以**原地覆盖** 1.02，用户不会被迫卸载（卸载即丢数据）。

### 2. V1.02 → V1.03 覆盖升级，数据是否保留（最高风险项）

用**最终发布版 APK**（含阶段五的写入顺序修复，sha256 `cc6201a8…`）重跑了一次完整链路。
此前那次验证用的是不含该修复的构建，而该修复恰好与数据完整性有关，所以必须重做。

步骤与结果：

| 步骤 | 结果 |
| --- | --- |
| 卸载旧应用，装干净的 V1.02 | `versionCode=3` / `versionName=1.02` |
| 在 V1.02 中创建分组 `V102Final` | 创建成功 |
| `adb install -r`（**不卸载**）装 V1.03 | `versionCode=4` / `versionName=1.03` |
| **分组是否迁移** | `V102Final` 出现在 V1.03 的「歌单」中 ✅ |
| 重启后是否仍在（迁移幂等） | 仍在 ✅ |
| 设置页版本号 | `MediaAnvil Mobile 1.03` ✅ |
| 冷启动 | 119–124 ms |

### 3. 发布产物本身的校验

从 GitHub Release 下载回来再校验一遍，而不是只信构建日志：

| 检查 | 结果 |
| --- | --- |
| Release | `MediaAnvil v1.03`，非 prerelease |
| 资产 | `MediaAnvil-v1.03.apk`、`MediaAnvil-v1.03.apk.sha256` |
| `.sha256` 与实际下载的 APK | **匹配**（`301ad7d3…20c5`） |
| APK 版本 | `versionCode=4` / `versionName=1.03` |
| APK 签名 | 校验通过，证书与 v1.02 一致 |

`.sha256` 的格式与 App 内更新逻辑兼容：`AppUpdateInstaller.parseExpectedSha256` 用
`[0-9a-f]{64}` 提取摘要，`sha256sum` 生成的 `"<hash>  <filename>"` 正好匹配。

### 4. 应用内更新检查

安装 1.03 后点「检查更新」，显示**「当前已经是最新版本」** —— 说明它确实读到了已发布的
Release 且没有误报新版本。

## 发布工作流

推送 `v1.03` 标签触发 `.github/workflows/release.yml`，各步骤全部 success：

1. 恢复 release keystore（从仓库 Secrets）
2. `:app:testDebugUnitTest :app:lintRelease :app:assembleRelease`
3. 校验 APK 签名，并断言标签与 `versionName` 一致
4. 生成 `MediaAnvil-v1.03.apk` 与 `.sha256`
5. 创建 GitHub Release 并上传两个资产

## 附：本阶段之前修掉的两个真实缺陷

阶段八本身只改版本号，但发布前发现并修复了两个会影响用户的问题，记录在此以便追溯：

1. **DataStore 写入顺序错乱导致丢数据**（阶段五引入 `SettingsStore` 时埋下）。
   `putAll` 把写入丢进 `Dispatchers.IO` 线程池，同一 key 的多次写入完成顺序不保证，
   旧的会覆盖新的。CI 抓到：连播三首后重启，播放历史只剩第一首。
   修复为显式串行链，并加了确定性的顺序测试（真机上 6 次都没复现该竞态，
   靠运气复现不能算测试）。

2. **真机 instrumented 测试永久卡死**（vivo 的 `fast_freezer` 在进程启动约 5 秒后冻结它，
   早于测试宿主 Activity 被拉起）。已在 `docs/testing/device-instrumented-tests-freeze.md`
   记录根因、无效的尝试与有效解法。修复后真机完整套件 **45 项全过，连续 3 次**。

## 结论

版本号与标签一致，签名与 v1.02 连续，覆盖升级不丢数据，发布产物校验和匹配，
Release 已创建。**v1.03 发布完成。**
