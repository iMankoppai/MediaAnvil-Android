# V1.03 阶段五验证记录：性能

测试日期：2026-09-23
设备：vivo V2520A（Android 16 / API 36），debug 包 `com.imankoppai.mediaanvil.debug`
工具链：JDK 17、Android SDK 36（Build Tools 36.0.0）、Gradle 9.6.0

## 方法：先测量，再优化

性能改动最容易变成「我觉得这样更快」。所以这一步的顺序是**先在真机上量出基线**，再动代码，最后用同一个测量方式对比。

新增 `androidTest/Phase5PerformanceTest.kt`（9 项），每项重复多次并取**最快值**（最快的一次最少受设备上其它工作干扰），结果以微秒记录。这些不是通过/失败断言——在共享 CI 机器上设一个墙钟阈值只会变得不稳定，失败原因还跟 App 无关。

`println` 在 instrumentation 进程里既不可靠地进原始输出流、也不可靠地进 logcat，所以测量结果同时写入文件，避免「量了但读不到」。

## 发现并修复的缺陷：媒体库在主线程做磁盘 I/O

`LibraryViewModel` 有三处主线程 I/O：

1. **`startup()`** 由 `LaunchedEffect` 在首帧组合时调用，却**同步**读 JSON 缓存（`LibraryCache.load`）。
2. **`attachKnownSidecars()`** 写在 `withContext(Dispatchers.IO)` **块之后**——`withContext` 返回后协程已经回到主线程，所以这段对每首歌发一次 SAF `findFile` 查询的代码跑在主线程上。库越大越卡。
3. **`LibraryCache.save()`** 同样在 IO 块之后，主线程写 JSON。

修复：把这三件事全部放进**同一个 IO 块**内，`withContext` 返回后主线程只做状态赋值。`startup()` 增加 `loading` 态，避免缓存到达前的那一帧闪出「没有音频文件」的空态文案。

### 效果

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 冷启动（5 次） | 347 / 299 / 305 / 298 / 287 ms | 262 / 251 / 252 / 257 / 263 ms |
| 主线程磁盘 I/O | 有（见下） | 无 |

冷启动中位数 **~300ms → ~255ms**。

功能未受影响：真机上 6 首歌全部正常显示，`列表/收藏/近期/歌单` 标签完好，此前的标签编辑结果 `DSH-TAG-OK` 仍保留，无空态闪烁。

## 回归测试：`Phase5MainThreadIoTest`（3 项）

用 StrictMode 的 `detectDiskReads` / `detectDiskWrites` 检测主线程 I/O，采用**收集**而非崩溃的 penalty，这样失败信息能指出具体调用点。

两个容易写错、我都踩过的地方：

1. **StrictMode 的线程策略是按线程生效的**，而 instrumentation 测试跑在测试线程、不是 App 主线程。第一版把策略装在测试线程上，等于盯错了线程——无论 App 怎么写都会通过。现在在 `Dispatchers.Main` 上安装与卸载。
2. **被测调用本身也要派发到 Main**。`startup()` 原先在调用者线程同步干活；从 `runBlocking` 直接调用，那段工作就跑在测试线程上，策略同样管不到。现在用 `withContext(Dispatchers.Main) { library.startup() }`。

### 已验证这个测试确实能抓到 bug

一个只在修好的代码上通过的测试毫无价值。所以把修复 `git stash` 掉、用**旧代码**重跑：

```
Tests run: 3,  Failures: 2
main-thread I/O from the library
main-thread I/O from a scan
```

失败栈精确指出问题所在：

```
StrictMode.onReadFromDisk
  → SharedPreferencesImpl.getStringSet
  → SafStorage.grantedTrees(SafStorage.kt:35)
  → SafStorage.findGrant / findSubtitle
  → LibraryViewModel.findSidecarLyrics(LibraryViewModel.kt:104)
  → LibraryViewModel.attachKnownSidecars(LibraryViewModel.kt:171)
```

恢复修复后同一测试 `OK (3 tests)`。**测试先证明会失败，再证明会通过**，才说明它有效。
