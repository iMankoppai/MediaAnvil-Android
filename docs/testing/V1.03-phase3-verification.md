# V1.03 阶段三验证记录：移除「所有文件访问」

测试日期：2026-09-23
设备：vivo V2520A（Android 16 / API 36），测试期间**处于锁屏状态**
工具链：JDK 17、Android SDK 36（Build Tools 36.0.0）、Gradle 9.6.0

## 本阶段改动

### 1. 权限

`AndroidManifest.xml`：

- **移除** `MANAGE_EXTERNAL_STORAGE`（「所有文件访问」）。
- **移除** `android:requestLegacyExternalStorage="true"`。
- 保留并按版本收敛读取权限：

| 权限 | 版本上限 | 用途 |
| --- | --- | --- |
| `READ_MEDIA_AUDIO` | — | Android 13+ 读取音频 |
| `READ_EXTERNAL_STORAGE` | `maxSdkVersion=32` | Android 12 及以下读取音频 |
| `WRITE_EXTERNAL_STORAGE` | `maxSdkVersion=29` | Android 10 及以下写入（作用域存储不适用） |

### 2. 音频扫描 → 媒体库

`DeviceAudioLibrary.scan` 不再使用 `DATA` 绝对路径与 `File.listFiles()`：

- API 29+ 使用 `RELATIVE_PATH`（如 `Music/sub/`），旧版本回退到 `DATA` 并转换为同样的相对形式。
- 文件夹过滤改为比较**相对路径**（`isFolderAllowed(relativeFolder, folders)`），不再依赖存储根路径。
- 找不到同目录歌词时不再报错，只是没有歌词。

### 3. 外挂歌词读写 → SAF 文件夹授权

新增 `SafStorage`，取代 `java.io.File` 直接操作：

- 文件夹通过 `ACTION_OPEN_DOCUMENT_TREE` 授权并持久化（`takePersistableUriPermission`）。
- `findGrant` 选择**最深匹配**的授权目录；`Music/live/` 优先于 `Music/`。
- `writeSubtitle` 在授权目录内创建歌词，并清理同名旧文件（含 `song.mp3.lrc` 旧命名）。
- `deleteSubtitle` 只允许删除歌词扩展名文件，且**拒绝删除音频文件本身**（`isSafeSubtitleName`）。

### 4. 标签编辑 → 媒体库写入请求

- API 30+ 先通过 `MediaStore.createWriteRequest` 取得用户对该音频的写入授权，再改写标签。
- 未获授权时不写入，并提示「系统未允许写入该文件，标签未做修改」。
- 写入后改用 `MediaScannerConnection.scanFile(uri)` 让媒体库刷新元数据。

### 5. 交互变化

- 首次进入媒体页：请求**音频读取权限**（不再是跳转「所有文件访问」设置页）。
- 首次保存歌词或编辑标签时：提示并打开文件夹选择器，授权一次后长期有效。

## 系统限制与影响（已在 `docs/design/V1.03-phase3-storage-migration.md` 说明）

1. **保存外挂歌词必须先选择一次文件夹。** 歌词不是媒体文件，MediaStore 不索引，Android 11+ 没有任何权限能让应用直接写音频同目录；这是移除宽权限的必然代价。
2. **标签编辑需要媒体库写入授权。** 用户拒绝时标签不写入，界面给出明确提示而不是静默失败。
3. **未授权文件夹中的音频仍可播放**，只是不能写歌词或改标签。
4. Android 10 及以下行为与之前一致。

#### 标签编辑的完整链路证据

1. 在标签编辑器点「保存标签」后，系统弹出 `com.android.providers.media.PermissionActivity`：
   **「要允许 MediaAnvil 修改这个音频文件吗？」**，即 `MediaStore.createWriteRequest` 生效。
2. 点「允许」后写入成功。直接解析产出文件的 ID3 帧：

```text
54 49 54 32 | 00 00 00 17 | 00 00 01 | FF FE | 44 00 53 00 48 00 2D 00 54 00 41 00 47 00 2D 00 4F 00 4B 00
 T  I  T  2     size 0x17     flags     BOM    D     S     H     -     T     A     G     -     O     K
```

即一个带 UTF-16LE BOM（`FF FE`）的 `TIT2` 帧，内容为 `DSH-TAG-OK`；文件哈希与原文不同、mtime 更新为写入时刻，
应用缓存中的 `title` 也同步变为 `DSH-TAG-OK`。

> 验证说明：首次校验曾误判为失败，原因是校验脚本按 ASCII/UTF-16BE 查找，
> 而 jAudioTagger 写入的是带 BOM 的 UTF-16LE；另有一次 `adb pull` 与写入发生竞态。
> 按字节偏移解析后确认写入成功——这是校验脚本的问题，不是功能缺陷。
